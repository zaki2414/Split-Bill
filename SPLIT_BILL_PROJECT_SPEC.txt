PROJECT OVERVIEW
================================================================================
Split Bill adalah aplikasi web untuk membagi pengeluaran grup (restoran, gocar, 
belanja bersama, dll) dengan fitur:
  1. Receipt scanning via OCR (Google Vision - foto struk → ekstrak items)
  2. Item-first allocation form (siapa aja yang makan menu ini?)
  3. Automatic settlement calculation (siapa bayar siapa)
  4. History & reporting
  5. Flexible item sharing (SHARED vs INDIVIDUAL allocation)
  6. Optional user registration for balance tracking

Key Insight:
  - Tidak perlu fixed groups → beda orang per split
  - Cukup input nama (text) → tidak wajib register
  - Payer selection mandatory → determine settlement flow
  - Item type selection → control allocation logic
  - Item-first allocation (faster than drag-drop, more natural)
  - Optional user account untuk track personal balance

Target: Portfolio project untuk showcase cloud deployment + smart UX design

DATABASE SCHEMA
================================================================================

DESIGN PHILOSOPHY:
  - No fixed groups or required registration
  - Flexible naming: just type person names (VARCHAR)
  - Optional user accounts for balance tracking
  - Payer selection is mandatory (determine settlement)
  - Item type selection controls allocation logic

-- Users (OPTIONAL - for account tracking only)
CREATE TABLE users (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  name VARCHAR(100) NOT NULL,
  email VARCHAR(100) UNIQUE,
  phone VARCHAR(20),
  avatar_url VARCHAR,
  created_at TIMESTAMP DEFAULT NOW(),
  updated_at TIMESTAMP DEFAULT NOW()
);

-- Receipt (core entity - minimal required fields)
CREATE TABLE receipts (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  
  -- WHO: People involved (as text, no FK required)
  uploaded_by VARCHAR(100),           -- who uploaded (optional text)
  payer_name VARCHAR(100) NOT NULL,   -- who paid this receipt (MANDATORY!)
  
  -- WHAT: Receipt details
  receipt_image_url VARCHAR,
  merchant_name VARCHAR(100),
  receipt_date TIMESTAMP,
  total_amount DECIMAL(10, 2) NOT NULL,
  notes TEXT,
  
  -- STATUS
  status VARCHAR(20) DEFAULT 'pending', -- 'pending', 'finalized', 'settled'
  
  created_at TIMESTAMP DEFAULT NOW(),
  updated_at TIMESTAMP DEFAULT NOW()
);

-- Items extracted from receipt (via OCR)
-- IMPORTANT: item_type determines allocation calculation
CREATE TABLE receipt_items (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  receipt_id UUID REFERENCES receipts(id) ON DELETE CASCADE,
  
  name VARCHAR(100) NOT NULL,
  category VARCHAR(50), -- 'food', 'drink', 'transport', 'other'
  
  -- For calculation
  total_price DECIMAL(10, 2) NOT NULL,
  quantity INT NOT NULL,  -- qty of this item in receipt
  unit_price DECIMAL(10, 2),  -- price per unit (if qty > 1)
  
  -- CRITICAL: Item allocation type
  -- SHARED: price divided equally among consumers
  --   e.g., Pizza (Rp60k, 3 people) → each pays Rp20k
  -- INDIVIDUAL: each person pays unit_price × qty they consumed
  --   e.g., Soda (Rp10k each, qty 3) → person pays Rp10k per soda
  item_type VARCHAR(20) NOT NULL, -- 'SHARED' or 'INDIVIDUAL'
  
  order_index INT, -- for display order
  created_at TIMESTAMP DEFAULT NOW()
);

-- Allocation (item assigned to person, with quantity)
-- person_name: flexible, just text (no FK to users table)
CREATE TABLE item_allocations (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  receipt_id UUID REFERENCES receipts(id) ON DELETE CASCADE,
  item_id UUID REFERENCES receipt_items(id) ON DELETE CASCADE,
  
  -- Person: just name, no FK (flexible!)
  person_name VARCHAR(100) NOT NULL,
  
  -- Quantity allocated to this person
  -- For SHARED: always 1 (or null, not used)
  -- For INDIVIDUAL: qty they consumed (e.g., 1 soda, 0.5 pizza)
  quantity_allocated DECIMAL(5, 2),
  
  created_at TIMESTAMP DEFAULT NOW(),
  updated_at TIMESTAMP DEFAULT NOW()
);

-- Settlement (auto-calculated: who owes who)
CREATE TABLE settlements (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  receipt_id UUID REFERENCES receipts(id) ON DELETE CASCADE,
  
  -- Both as text (flexible, matches person_name from allocations)
  payer_name VARCHAR(100) NOT NULL,    -- who will receive money
  ower_name VARCHAR(100) NOT NULL,     -- who will pay
  
  amount DECIMAL(10, 2) NOT NULL,
  status VARCHAR(20) DEFAULT 'pending', -- 'pending', 'paid', 'cancelled'
  paid_at TIMESTAMP,
  notes TEXT,
  
  created_at TIMESTAMP DEFAULT NOW(),
  updated_at TIMESTAMP DEFAULT NOW()
);

-- Payment history (optional - for tracking actual transfers)
CREATE TABLE payments (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  settlement_id UUID REFERENCES settlements(id),
  
  sender_name VARCHAR(100),           -- who sent money
  receiver_name VARCHAR(100),         -- who received
  
  amount DECIMAL(10, 2),
  payment_method VARCHAR(50),         -- 'manual', 'transfer', 'cash'
  proof_url VARCHAR,                  -- optional screenshot
  paid_at TIMESTAMP DEFAULT NOW()
);

-- Personal Balance Tracking (optional, for registered users)
-- Matches person_name with user accounts when they register
CREATE TABLE person_to_user (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  person_name VARCHAR(100) NOT NULL,  -- from allocations/settlements
  user_id UUID REFERENCES users(id),  -- linked account
  created_at TIMESTAMP DEFAULT NOW()
);


FEATURES BREAKDOWN
================================================================================

1. AUTHENTICATION
   - Optional: Email-based registration (for balance tracking)
   - No password required: Email magic link or anonymous
   - Authorization: Registered users can see their personal balance
   - Unregistered: Can still create/view receipts with just names
   - Optional: Google/Facebook OAuth for convenience

2. RECEIPT UPLOAD & OCR (Google Vision Free Tier)
   
   Why Google Vision Free Tier?
   - Free: 300 requests/month (covers MVP)
   - Accuracy: 95% (same as Claude Vision)
   - Speed: 1-2 seconds
   - Cost: FREE for MVP phase, then $1.50/1000 req
   - Setup: Easy (Google Cloud API key)
   
   Flow:
   1. User upload receipt image
   2. MANDATORY: Select "Who paid this receipt?" (payer_name)
   3. Backend call Google Vision API
   4. Parse response → extract items (name, qty, price)
   5. Store in receipt_items table
   6. Show extracted items for review/correction
   7. Fallback: Manual entry if OCR fails

   Google Vision API Configuration:
   - Endpoint: google.cloud.vision.ImageAnnotatorClient()
   - Model: TEXT_DETECTION (for receipt text)
   - Language: Supports Indonesian (bahasa Indonesia)
   - Response: Structured text with confidence scores
   - Error handling: Try OCR, fallback to manual if >5 sec

   Implementation:
   - Create Google Cloud project
   - Enable Vision API
   - Generate API key (not OAuth, simpler)
   - Add to .env: GOOGLE_VISION_API_KEY
   - Call API with base64 image data
   - Parse TEXT_DETECTION response
   - Extract items from response

   Future Enhancement (V2+):
   - Add PaddleOCR fallback (if Google fails)
   - Hybrid: PaddleOCR first (free) → Google (fallback)
   - Reduces API cost when both work

3. DRAG-DROP ALLOCATION UI
   UI Layout:
   - Left panel: Available items (showing qty remaining)
   - Right panel: Person columns (dynamic, as many as needed)
   
   Interaction:
   - Drag item → drop to person column
   - Item qty decreases in available pool
   - When 100% allocated: Item disappears from left panel
   - Click X on item to remove from person (returns to pool)
   - Backend auto-saves after each action

   Item Type Behavior:
   - SHARED item: Consuming person contributes to shared allocation
     * Allocation UI shows: "Pizza - You + 2 others"
     * Price calculated at settlement: total ÷ 3
   
   - INDIVIDUAL item: Quantity matters
     * Allocation shows: "Soda ×1", "Soda ×2", etc
     * Price per person: unit_price × qty allocated

   States Display:
   - Item fully allocated: Greyed out, disappears from available
   - Item partially allocated: Show "3/5 allocated" remaining
   - Item unallocated: Highlight in warning color
   - Person total: Auto-update as items drag-dropped

4. ITEM-FIRST ALLOCATION FORM (MVP - Simple & Fast)
   
   Why Item-First vs Person-First?
   - Real-world behavior: Groups discuss PER ITEM (not per person)
   - Example: Waiter asks "Ikan Bakar siapa?" → group answers together
   - Speed: ~1-2 minutes (vs 2-3 min for person-first)
   - Natural conversation flow
   - Better for group dynamics
   - Less error-prone (group confirms together)

   Flow:
   1. Upload receipt + select items
   2. System shows form for each item:
      "Ikan Bakar Matah (Rp40k) - Siapa aja yang makan?"
      [✓] Adi
      [✓] Candra
      [ ] Budi
      [ ] Diana
      [ ] Eka
      [ ] Fiona
      [ ] Gita
      [ ] Hendy
      
   3. User checks boxes for each person who consumed that item
   4. Next item: "Ikan Bakar Tauco (Rp50k) - Siapa aja?"
   5. Repeat until all items allocated
   6. System validates (everyone has allocation) + calculates settlement

   Advantages:
   - ✓ Fastest allocation method (~1-2 min)
   - ✓ Handles ambiguous items perfectly
   - ✓ Natural group conversation flow
   - ✓ Less individual decision fatigue
   - ✓ Group verification (less mistakes)
   - ✓ Simple to implement (forms + checkboxes)
   - ✓ No AI needed (works 100% of time)

   Implementation:
   - Create form per item
   - Checkboxes for person selection
   - Show item type + price for clarity
   - Auto-advance to next item
   - Summary at end before confirm

   Edge cases handled:
   - Shared dishes (multiple people check same item)
   - Individual items (1 person checks)
   - Mixed types (both shared and individual)
   - Ambiguous items (no guessing needed)

5. SETTLEMENT CALCULATION & SUMMARY (AUTO-CALCULATED)
   
   Core Logic:
   - For each person: Calculate total_owed based on item_type
   - Payer (who paid receipt) receives from others
   - Generate settlement records

   Calculation Per Item Type:

   A. SHARED Item Calculation:
      - Pizza (SHARED, Rp60k, 3 consumers)
      - For each consumer:
        * Check if they're in item_allocations for this item
        * If yes: allocated_price = total_price / count(consumers)
        * Rp60k / 3 = Rp20k each
      
   B. INDIVIDUAL Item Calculation:
      - Soda (INDIVIDUAL, Rp10k unit_price, qty 3)
      - For each consumer:
        * allocated_price = unit_price × quantity_allocated_to_person
        * Adi (qty 1): Rp10k × 1 = Rp10k
        * Budi (qty 1): Rp10k × 1 = Rp10k
        * Candra (qty 1): Rp10k × 1 = Rp10k

   Complete Pizza Hut Example:
   Receipt: Payer = Adi, Total = Rp120k
   
   Items:
   - Pizza (Rp60k, SHARED)
   - Soda (Rp30k, INDIVIDUAL, Rp10k each, qty 3)
   - Nugget (Rp30k, INDIVIDUAL, qty 1)
   
   Allocations:
   - Adi: Pizza (SHARED), Soda ×1
   - Budi: Pizza (SHARED), Soda ×1, Nugget ×1
   - Candra: Pizza (SHARED), Soda ×1
   
   Calculation:
   Adi consumed:
     * Pizza: Rp60k / 3 = Rp20k (SHARED)
     * Soda: Rp10k × 1 = Rp10k (INDIVIDUAL)
     * Total: Rp30k
   
   Budi consumed:
     * Pizza: Rp60k / 3 = Rp20k (SHARED)
     * Soda: Rp10k × 1 = Rp10k (INDIVIDUAL)
     * Nugget: Rp30k × 1 = Rp30k (INDIVIDUAL)
     * Total: Rp60k
   
   Candra consumed:
     * Pizza: Rp60k / 3 = Rp20k (SHARED)
     * Soda: Rp10k × 1 = Rp10k (INDIVIDUAL)
     * Total: Rp30k
   
   Settlement (Adi paid Rp120k total):
   - Adi consumed: Rp30k
     * Adi is owed: Rp120k - Rp30k = Rp90k
   - Budi consumed: Rp60k
     * Budi owes Adi: Rp60k
   - Candra consumed: Rp30k
     * Candra owes Adi: Rp30k
   
   Result:
   - Budi → Adi: Rp60k ✓
   - Candra → Adi: Rp30k ✓
   - Total match: Rp90k ✓

6. HISTORY & REPORTING

   - Statistics: Total spent, average per person

7. OPTIONAL: AI TRAINING

API ENDPOINTS
================================================================================

Authentication (Optional):
  POST   /api/auth/signup           - Create account (email + name)
  POST   /api/auth/login            - Email magic link
  GET    /api/auth/verify/:token    - Verify email
  POST   /api/auth/logout           - Logout

Receipts (Core Endpoints):
  POST   /api/receipts/upload       - Upload image + OCR
    Body: {
      image: base64_or_file,
      payer_name: "Adi",            ← MANDATORY
      receipt_date: "2024-01-15",
      merchant_name: "Pizza Hut"
    }
    Response: {
      receipt_id: "uuid",
      extracted_items: [{
        name: "Pizza",
        total_price: 60000,
        quantity: 1,
        item_type: "SHARED"           ← Default: need user selection
      }]
    }

  GET    /api/receipts/:id          - Get receipt details
  PUT    /api/receipts/:id          - Update payer_name, merchant, notes
  DELETE /api/receipts/:id          - Delete receipt

Items (with item_type):
  GET    /api/receipts/:id/items    - List all items
  PUT    /api/receipts/:id/items/:itemId - Update item
    Body: {
      item_type: "SHARED" or "INDIVIDUAL",
      name: "Pizza",
      total_price: 60000,
      quantity: 1,
      unit_price: 60000
    }

Allocations (Item-First Form):
  POST   /api/allocations/batch      - Create multiple allocations at once
    Body: {
      receipt_id: "uuid",
      allocations: [
        {
          item_id: "uuid",
          person_names: ["Adi", "Candra"]  ← Multiple people per item
        },
        {
          item_id: "uuid",
          person_names: ["Budi", "Eka"]
        }
      ]
    }
    Response: {
      success: true,
      allocation_count: 8,
      validation_warnings: []
    }
  
  GET    /api/receipts/:id/allocation-form - Get form data
    Response: {
      receipt_id: "uuid",
      items: [
        {
          id: "uuid",
          name: "Ikan Bakar Matah",
          price: 40000,
          type: "SHARED",
          order: 1
        },
        ...
      ],
      people: ["Adi", "Budi", "Candra", ...]
    }
  
  GET    /api/allocations/:receipt_id/summary - Get allocation summary
    Response: {
      allocations: {
        "Adi": ["Ikan Matah", "Soto", "Teh"],
        "Budi": ["Ikan Tauco", "Gado", "Kopi"],
        ...
      },
      status: "ready_to_calculate"
    }

Settlements (Auto-calculated):
  GET    /api/settlements/:receiptId - Get all settlements
    Response: [{
      payer_name: "Adi",            ← Who receives
      ower_name: "Budi",            ← Who pays
      amount: 60000,
      status: "pending"
    }]
  
  POST   /api/settlements/:id/pay   - Mark settlement as paid
    Body: { status: "paid", notes: "Transferred via Gopay" }

Personal Balance (Optional, for registered users):
  GET    /api/balance/:person_name  - Get balance for person
    Response: {
      person_name: "Adi",
      total_owed_to_me: 90000,      ← Others owe Adi
      total_i_owe: 0,                ← Adi owes to others
      net_balance: 90000,
      transactions: [...]
    }

Reports:
  GET    /api/reports/receipt/:id/pdf - Export receipt as PDF
  GET    /api/reports/personal/:person_name - Personal statement

Issue 1: OCR confidence low
  Solution: Show manual edit option, allow user to fix

Issue 2: Receipt date parsing fails
  Solution: Let user set date manually

Issue 3: Currency parsing (Rp vs others)
  Solution: Detect from receipt or user preference

Issue 4: Drag-drop not working on mobile
  Solution: Implement tap-to-select alternative on mobile

Issue 5: Settlement calculation wrong
  Solution: Show detailed breakdown per person, user can verify

Issue 6: Database connection timeout

ALLOCATION STRATEGY RATIONALE
================================================================================

Why Item-First (Not Person-First or Drag-Drop)?
---------------------------------------

Three possible approaches:

A. PERSON-FIRST: "Adi, apa yang kamu makan?"
   - Pro: Most intuitive for individual
   - Con: Tedious (must ask 8 people individually)
   - Time: ~2-3 minutes
   - Use case: 2-3 people only

B. ITEM-FIRST: "Ikan Matah siapa aja?" ⭐ CHOSEN
   - Pro: Fast (1-2 min), natural group conversation
   - Pro: Mirrors real-world (waiter asks per item)
   - Pro: Group discusses together, less mistakes
   - Pro: Handles all edge cases perfectly
   - Time: ~1-2 minutes
   - Use case: Any group size, any receipt type

C. DRAG-DROP: Visual allocation UI
   - Pro: Visually intuitive
   - Con: Tedious for many items (drag 50+ times)
   - Con: Mobile unfriendly
   - Time: ~3-5 minutes
   - Use case: UI showcase, but slow

DECISION: Use Item-First (B) for MVP because:
  ✓ Fastest method (1-2 min)
  ✓ Natural conversation flow (group talks together)
  ✓ Real-world behavior (how restaurants work)
  ✓ Handles ambiguous items perfectly (multiple ikan varieties)
  ✓ Simple implementation (forms + checkboxes)
  ✓ 100% accurate (no guessing from AI)
  ✓ Scalable (works for any group size)

Future: Add drag-drop (V2) as visual alternative


DATA MODEL DESIGN RATIONALE
================================================================================

Why Flexible Naming (No Fixed Groups)?
---------------------------------------
1. Real-world usage: Different people per split
   - Monday: Split with Alice, Bob, Charlie (restaurant)
   - Wednesday: Split with Diana, Eve, Frank (transport)
   - Friday: Split with Alice, Henry (groceries)

2. Zero friction: No registration required
   - Just type names → immediate allocation
   - No account setup overhead
   - Perfect for one-time or casual splits

3. Optional tracking: User can register later
   - If Alice registers: her balance aggregated
   - Past allocations linked to her account
   - Still works without registration

Database Benefits:
  ✓ Simpler schema (no groups, no memberships)
  ✓ Flexible (anyone can be in receipt)
  ✓ Scalable (no complex FK relationships)
  ✓ User registration is pure convenience layer

Item Type Logic (SHARED vs INDIVIDUAL)
--------------------------------------
Why two types?

SHARED Items:
  - Pizza, entrees, shared dishes
  - Price divided equally among who consumed it
  - Formula: total_price / count(consumers)
  - Example: Rp60k pizza / 3 people = Rp20k each

INDIVIDUAL Items:
  - Beverages, personal items, individual orders
  - Each person pays unit_price × qty they got
  - Formula: unit_price × quantity_allocated
  - Example: Rp10k soda × 1 per person

Real Example (Pizza Hut):
  - Pizza (Rp60k, SHARED, 3 people): Rp20k each
  - Soda (Rp30k, INDIVIDUAL, 3×Rp10k): Rp10k per soda
  - Nugget (Rp30k, INDIVIDUAL, only Budi): Rp30k to Budi

Payer Selection (Mandatory)
---------------------------
Why mandatory?

Without payer, system doesn't know:
  - Who should receive money
  - Who owes whom
  - How to calculate settlement

With payer = receipt paid by Adi:
  - Adi paid full amount (Rp120k)
  - Adi consumed some items (Rp30k)
  - Adi is owed difference (Rp90k)
  - Others pay Adi according to their consumption

Flow Example:
  1. Upload receipt
  2. Select payer: "Adi"
  3. Extract items + select types
  4. Allocate items to people
  5. System calculates:
     * Adi consumed: Rp30k
     * Settlement: Others owe Adi Rp90k

This design allows:
  ✓ Any person can be payer (not just receipt owner)
  ✓ Flexibility in group composition
  ✓ Accurate settlement calculation
